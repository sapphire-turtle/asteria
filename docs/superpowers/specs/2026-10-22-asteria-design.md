# project-asteria 設計書

- 日付: 2026-10-22
- 状態: レビュー待ち

## 1. 目的とスコープ

AIエージェントに整理を手伝ってもらえる、セルフホストの**画像管理アプリ（asteria-photos）**と**音楽再生アプリ（asteria-music）**を作る。

### 要件

1. サーバー・クライアント型。クライアントは egui のネイティブアプリ（デスクトップと iOS）。Web クライアントは将来の検討事項とする。
2. クライアントは、低解像度の画像や低音質の音声を任意でローカルにキャッシュでき、オフラインでも閲覧・再生できる。
3. エンドユーザー向けの CLI は作らない。AIエージェント向けに MCP を提供し、ファイル整理やプレイリスト作成を任せられるようにする。
4. **原本はファイル、DB はキャッシュ**。DB はいつ消しても原本から作り直せること。マイグレーションは書かない。
5. 特定のアプリにロックインされないよう、メタデータは標準形式（XMP、M3U8、埋め込みタグ）に寄せる。
6. iPhone の写真を、アプリを開いている間に一括でアップロードできる。バックグラウンドでのアップロードは不要。
7. iPhone でも music を使う。画面ロック中や他のアプリを使っている間も再生を続ける（バックグラウンド再生）。
8. クライアントには複数のサーバーを登録でき、手軽に切り替えられる（2026-10-25 追加）。同時につなぐのは1つだけ。

### スコープ外（意図的に入れないもの）

- 汎用のマルチメディアビューアやファイラー（3D、PDF など）にはしない。photos は写真と動画、music は音楽だけを扱い、それ以外の画像はジャケットとしてのみ表示する。
- 近似検索（ベクトル）。キャッシュとして後から追加できる設計にしておき、今回は実装しない。
- 複数ユーザー向けの認証と権限管理。**保存形式**は最初から複数ユーザーに対応させるが、**実装**は単一ユーザー（トークン1本）で始める。
- 複数サーバーへの同時接続（登録と切り替えは要件8で扱う）、Web クライアント、photos のバックグラウンドアップロード。
- エージェント用の MCP ゲートウェイ（photos と music の両方を束ねるもの）。必要になったら追加する。

### 想定する運用

- サーバーは自宅で動かし、LAN か VPN（Tailscale など）経由でアクセスする。
- `~/Vault/Pictures` を asteria-photos-server が、`~/Vault/Music` を asteria-music-server が公開する。
- 改修したらすぐ本番に投入する。問題が起きたらキャッシュを消して作り直す。

## 2. 全体構成

1つの git リポジトリ（`sapphire-turtle/project-asteria`）に、Cargo ワークスペースとして次のクレートを置く。

```
project-asteria/
├─ crates/                              ライブラリクレート
│  ├─ asteria-framework-api/     MIT OR Apache-2.0  共通の wire 型
│  ├─ asteria-photos-api/        MIT OR Apache-2.0  photos の wire 型（framework-api を re-export）
│  ├─ asteria-music-api/         MIT OR Apache-2.0  music の wire 型（framework-api を re-export）
│  ├─ asteria-framework/         GPL-3.0-or-later   コア（ライブラリ、XMP、ハッシュ、ジャーナル、計画、操作ログのマージ）
│  ├─ asteria-framework-server/  GPL-3.0-or-later   HTTP（JSON-RPC＋バイナリ）、認証、DB キャッシュ、MCP、メディア処理
│  └─ asteria-framework-client/  GPL-3.0-or-later   接続、オフラインキャッシュ、操作キュー、egui の共通部品
├─ photos-server/   asteria-photos-server  GPL-3.0-or-later  bin
├─ photos/          asteria-photos         GPL-3.0-or-later  bin（デスクトップと iOS。Xcode ラッパーは ios/ に置く）
├─ music-server/    asteria-music-server   GPL-3.0-or-later  bin
└─ music/           asteria-music          GPL-3.0-or-later  bin（デスクトップと iOS。Xcode ラッパーは ios/ に置く）
```

ライブラリクレートは `crates/` にクレート名のまま置き、バイナリクレートはリポジトリ直下に `asteria-` を除いた短い名前のディレクトリで置く（パッケージ名は `asteria-` 付き）。

### 依存の向き

- `asteria-framework-api` は何にも依存しない。依存してよいのは serde と ID 型だけ。
- `asteria-photos-api` と `asteria-music-api` は `asteria-framework-api` に依存し、それを re-export する。
- `asteria-framework` は `asteria-framework-api` に依存する。`-server` と `-client` は `asteria-framework` に依存する。
- 各アプリは、framework の該当クレートと自分の `*-api` に依存する。photos と music は互いに依存しない。
- サーバーとクライアントを別クレートにするのは、サーバーに egui を、クライアントに ffmpeg や vips を持ち込まないため。
- 現状、photos の閲覧用 DTO（`MediaItem`、`LibraryInfo`、`FolderListing` など）は `asteria-framework-api` にある。これらを変えると、photos-api と music-api の両方のメジャーバージョンが上がる。music 側に関係のない変更が増えるようなら、後で photos-api に移す。

### バージョン管理

- `*-api` の3クレートは、それぞれ単独でバージョンを管理する。**メジャーバージョン＝API バージョン**とする。
- バージョンを代表するのはアプリ側の API（`asteria-photos-api` / `asteria-music-api`）。クライアントはハンドシェイクで、このバージョンだけを確認する。
- `asteria-framework-api` に破壊的変更を入れたら、photos-api と music-api の両方のメジャーバージョンを上げる。
- `*-api` 以外のクレートは、ワークスペースで共通のバージョンにする。

### ライセンス

- `*-api` は MIT OR Apache-2.0、それ以外は GPL-3.0-or-later とする。
- GPL のクレートには、sapphire の desktop と同じ App Store マーケットプレイス例外（GPLv3 第7条の追加許可）を付ける。テンプレートは `sapphire-journal/desktop/LICENSE.App-Store-Exception`。
- `cargo deny` で依存ライブラリのライセンスを寛容なものに限る。GPL を許可するのは asteria 自身のクレートだけにする。

### 主要技術

| 用途 | 採用するもの |
|---|---|
| HTTP サーバー | axum |
| RPC | HTTP 上の JSON-RPC（sapphire、MCP と揃える） |
| MCP | rmcp（Streamable HTTP、`/mcp`） |
| DB キャッシュ | redb |
| GUI | eframe / egui |
| 音声タグ | lofty |
| EXIF | nom-exif 系 |
| 画像・動画・音声の変換 | ffmpeg、libvips（`vips` コマンド）を子プロセスとして呼ぶ |
| 音声デコードと出力（クライアント） | symphonia、cpal |

| ハッシュ | BLAKE3 |

## 3. 原本ファイルの形式

### 3.1 ライブラリの配置

置き場所は、中身の性質で3つに分ける（2026-10-27 決定）。

- **ワークスペース**（ライブラリルート）：ライブラリそのものと、ほかのアプリも読むものだけを置く。メディア、サイドカー、M3U プレイリスト、`library.toml`（ライブラリの ID）、`users.toml`（メンバー）、ゴミ箱。
- **データディレクトリ**（`<data_dir>/<アプリ名>/<ライブラリID>/`）：サーバーのインスタンスごとの内部データ。ジャーナル、整理計画、保存した検索、未確定のアップロード、サーバーのロック。
- **キャッシュディレクトリ**（`<cache_dir>/<アプリ名>/<ライブラリID>/`）：消しても作り直せるもの。

```
<ライブラリルート>/                  例: ~/Vault/Pictures
├─ .asteria/
│  ├─ library.toml                   形式番号（format = 1）、ライブラリ ID（UUID）、オーナーのユーザー ID
│  ├─ users.toml                     ユーザー ID と表示名の対応（[[user]] の配列）
│  ├─ trash/<op-id>/…                ゴミ箱（元のパスを保持する）
│  └─ playlists/<user-id>/*.m3u8     music：個人のプレイリスト
│     playlists/shared/*.m3u8        music：共有のプレイリスト
├─ Inbox/                            photos：アップロードの受け取り先
└─ 2025/京都旅行/IMG_0001.HEIC
   2025/京都旅行/IMG_0001.HEIC.xmp

<data_dir>/<アプリ名>/<ライブラリID>/  例: ~/.local/share/asteria-photos/<ライブラリID>/
├─ server.lock                       このホストで、このライブラリを扱うサーバーは1つだけ（§4.1）
├─ journal/YYYY-MM.jsonl             実行した操作の記録（追記のみ）
├─ plans/<plan-id>.toml              整理計画（承認待ち、実行済み、却下）
├─ searches/<user-id>/*.toml         photos：保存したタグ検索（仮想アルバム）
└─ uploads/<session>/                確定前のアップロード（チャンクを書き込む途中のファイル）
```

- ユーザー ID は、名前ではなく、変わらない短い ID にする。sapphire と揃えて grain-id（例：`123abcd`）を使う。
- `library.toml` は、まず `format` だけを読む。対応していない形式番号なら、ほかの項目の形が違っていても「対応していない形式」として報告する。
- 認証トークンはライブラリに入れず、サーバーの設定ディレクトリに置く。ライブラリはバックアップや同期の対象になり得るため。
- DB キャッシュ、サムネイル、変換結果は `<cache_dir>/<アプリ名>/<ライブラリID>/`（Linux では `~/.cache/…`）に置く。丸ごと削除しても再生成できる。
- ゴミ箱をワークスペースに残すのは、削除を同じファイルシステムの中の rename にするため。
- 以前の版がワークスペースの `.asteria/` に置いた `journal/`、`uploads/`、`server.lock` は、移しも消しもしない（別のインスタンスのものかもしれない）。見つけたら起動時に一度ログに出す。

#### ワークスペースを複数のインスタンスで共有する

1つのワークスペースを NFS などで共有し、別々のホストのサーバーが同時に扱ってよい（本番と試験用のサーバーなど）。

- ジャーナル、キャッシュ、未確定のアップロードは、インスタンスごとに持つ。あるインスタンスで行った操作は、ほかのインスタンスのジャーナルには載らない（取り消しもそのインスタンスでしかできない）。
- ファイルの監視は、ほかの NFS ホストからの変更に気づかない。そうした変更は、定期的な再スキャン（15分ごと）か `library.rescan` で反映される。
- 重複の確認は、そのインスタンスがスキャンしたものしか知らない。
- 同じホストで同じライブラリのサーバーを2つ動かすことはできない（データディレクトリとキャッシュディレクトリを共有してしまう）。2つ目は `server.lock` を取れずに終わる。
- 一時ファイルの名前にはプロセスごとのタグが入り、起動時の掃除は 24 時間より古いものだけを消す（§3.3、§4.2）。そのため、ほかのインスタンスが書き込み中の一時ファイルを消すことはない。
- 2つのインスタンスから同じ項目を同時に編集したときは、後に書いた方が残る（last-writer-wins）。

### 3.2 フォルダとタグ（photos）

- フォルダがアルバムになる。
- アルバムをまたぐ分類は、XMP の階層タグ（`lr:hierarchicalSubject`）で表す。
- 仮想アルバムは、タグ検索の条件を保存したもの（`searches/`）として表す。写真を列挙した独自の一覧ファイルは作らない。

### 3.3 サイドカー（XMP）

画像も音声も、メディアの横に `<メディア名>.<拡張子>.xmp` を置く（darktable 方式）。

- **必要になったときだけ作る。** 評価やタグなど、保存すべき情報が初めてできた時点で作成し、ハッシュもそのとき書き込む。
- 標準の項目
  - `xmp:Rating`：オーナーの評価
  - `dc:subject`、`lr:hierarchicalSubject`：タグ
  - `dc:description`：説明
  - `xmp:Label`：色ラベル
- `asteria:` 名前空間（独自）
  - `ContentHash`：`blake3:<hex>`
  - `HashScope`：`media-payload/1` か `file/1`
  - `FileHash`：メディアのファイル全体のハッシュ（`file/1`、`blake3:<hex>`）。asteria がサイドカーを書くたびに、その時点の値に更新する。payload ハッシュが同じファイルが複数あるときに、紐付け直しの候補を絞るのに使う（§4.2）
  - `UserRatings`：オーナー以外のユーザーの評価（ユーザー ID、値、更新時刻）
  - `RatingModified`：オーナーの評価の更新時刻（オフライン編集の後勝ち判定に使う）
- 書き込みは、一時ファイルに書いてから rename するアトミックな方法で行う。
- asteria が知らない項目は、そのまま保持して書き戻す。
- XMP として読めない（壊れている、手で編集して不正になった）場合は、上書きしない。そのファイルに警告を付け、直るまで読み取り専用にする。

読み取りの規則

- `ContentHash` と `HashScope` は2つ揃って意味を持つ。片方だけのとき、および知らない `HashScope`（新しい版が書いた `media-payload/2` など）のときは、ハッシュが無いものとして扱う（再計算できるため）。`HashScope` が既知で `ContentHash` の文字列が不正なら、壊れたサイドカーとする。
- `FileHash` は無くてもよい（古いサイドカーや、他のツールが書いたもの）。文字列が不正なら、壊れたサイドカーとする。
- 評価、ハッシュ、ユーザー ID、日時のどれかが不正なら、サイドカーは壊れているものとして読み取り専用にする。
- `Rating` は整数値の実数（`4.0` など）も受け付ける。小数部のある値は不正とする。
- XMP の日時は精度を落とした形（`YYYY`、`YYYY-MM-DDThh:mm` など）も受け付ける。タイムゾーンが無ければ UTC とみなす。
- `UserRatings` に同じユーザーが複数あるときは、`Modified` が最も新しいものを採る。
- 16 MiB を超えるファイル、要素の入れ子が 128 段を超えるファイルは、壊れたサイドカーとして扱う（大きすぎるファイルは最後まで読まない）。

書き込みの規則

- 書き直すのは、値が変わった asteria の管理項目だけにする。変わっていない項目は、元のバイト列のまま残す。
- 説明を消したときは、`dc:description` を他の言語の項目ごと取り除く。
- 書き出したバイト列は、書き込む前にパースし直して確認する。管理項目の読み戻した値が一致しなければ、書き込みを拒否する。
- 一時ファイルの名前は `.<名前>.<タグ>.asteria-tmp` にする。タグはプロセスごとにランダムに決めるので、落ちた以前の実行やほかのインスタンスの一時ファイルが、新しい書き込みを妨げることはない。同じプロセスの一時ファイルが残っている間（書き込み中）は、そのファイルへの書き込みを拒否する。残ったものは起動時に掃除する（§4.2、§6）。タグのない以前の形（`.<名前>.asteria-tmp`）も一時ファイルとして扱う。
- 書き戻しで失われるもの：ルート要素の外側にある内容（コメント、処理命令など）は落ちる。XML 宣言は `<?xml version="1.0" encoding="UTF-8"?>` に正規化する。xpacket で包まれていたファイルは、標準の `begin`/`id` と `end="w"` で包み直す。
- 時刻は RFC 3339 の UTC で書く。端数がなければ秒まで、端数があれば必要な桁数（3/6/9桁）の小数部を書く。

```xml
<x:xmpmeta xmlns:x="adobe:ns:meta/">
 <rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#">
  <rdf:Description
    xmlns:xmp="http://ns.adobe.com/xap/1.0/"
    xmlns:asteria="https://sapphire-turtle.github.io/ns/asteria/1.0/"
    xmp:Rating="4"
    asteria:RatingModified="2026-10-22T09:00:00Z"
    asteria:ContentHash="blake3:9f2c…"
    asteria:HashScope="media-payload/1"
    asteria:FileHash="blake3:41ab…">
   <asteria:UserRatings><rdf:Bag>
    <rdf:li asteria:User="123abcd" asteria:Rating="5" asteria:Modified="2026-10-21T20:00:00Z"/>
   </rdf:Bag></asteria:UserRatings>
  </rdf:Description>
 </rdf:RDF>
</x:xmpmeta>
```

### 3.4 payload ハッシュ

メタデータ部分を除いた、符号化データだけのハッシュ（BLAKE3）。タグや EXIF を書き換えても変わらない。

| 形式 | ハッシュ対象 | 除外するもの | 対応段階 |
|---|---|---|---|
| JPEG | SOI、APP0〜15/COM 以外のすべてのセグメント（SOF/DQT/DHT/SOS のほか DRI/DAC/DNL/JPGn も）、圧縮データ（スタッフィングと RST を含む）、EOI | APP0〜15、COM、フィルバイト、最初の EOI より後ろ | 第1段階 |
| PNG | IHDR、PLTE、IDAT、IEND、および画素の内容を表す tRNS、APNG の acTL/fcTL/fdAT | その他の補助チャンク（tEXt、iTXt、eXIf、tIME、iCCP など）、チャンクの長さと CRC、IEND より後ろ | 第1段階 |
| WebP | VP8、VP8L、ALPH、ANIM、ANMF | VP8X（メタデータ有無のフラグを含むため）、EXIF、XMP、ICCP、未知のチャンク、チャンクのサイズとパディング、RIFF サイズより後ろ | 第1段階 |
| FLAC | メタデータの終わりからファイルの終わりまで（フレームは解析しない） | 先頭の ID3v2、すべてのメタデータブロック（STREAMINFO を含む）、末尾の ID3v1/APEv2 | 第1段階 |
| MP3 | 先頭の ID3v2 と末尾の ID3v1/APEv2 の間のバイト列（フレームは解析しない） | ID3v2、ID3v1、APEv2（Lyrics3 は除外しない） | 第1段階 |
| HEIC / AVIF | 主画像アイテムのデータ | Exif、XMP アイテム | 第2段階 |
| M4A（AAC / ALAC） | `mdat` の中身 | `moov/udta` など | 第2段階 |
| Ogg Vorbis / Opus | 音声パケット（ページ単位ではなくパケット単位で読む） | コメントヘッダ | 第2段階 |
| RAW、動画、その他 | ファイル全体（`file/1`） | ― | 当面このまま |

- 第1段階の形式の補足
  - JPEG：先頭の SOI の後、圧縮データの外（トップレベル）に長さを持たないマーカー（2つ目の SOI、RST、TEM など。EOI は除く）が現れたら、`file/1` に切り替える。
  - PNG：IHDR が先頭に無い、または IDAT/fdAT が1つも無ければ `file/1` にする。
  - WebP：画像のチャンク（VP8、VP8L、ANMF のどれか）が必要。無ければ `file/1` にする。
  - FLAC、MP3：対象のバイト列が0バイトなら `file/1` にする。
- 形式は拡張子ではなく先頭のマジックバイトだけで判定する。ID3v2 の後ろに `fLaC` があれば FLAC と判定する。MP3 は同期ワードに加えてフレームヘッダーを確かめる（バージョン、レイヤー、ビットレート番号、サンプルレート番号が予約値でないこと）。
- 形式として壊れているメディアは、理由を残して `file/1` に切り替える。
- デコード後のピクセルや波形のハッシュは使わない。デコーダのバージョン差で値が変わるため。
- `HashScope` にはバージョンを付ける。形式ごとの切り出し方を変えたら番号を上げる。
- 対応形式が増えたときは、サイドカーのハッシュを書き直すことで移行する。

### 3.5 プレイリスト（M3U8）

- UTF-8 で書き、先頭に `#EXTM3U` を置く。パスはプレイリストファイルからの相対パスにする。
- 各エントリの直前に `#ASTERIA-HASH:blake3:<hex>` を置き、ファイルが移動しても追跡できるようにする。他のプレイヤーは知らない `#` 行を無視する。
- 評価別のプレイリストを作る場合は、サイドカーから生成した出力物として扱う。原本にはしない。

### 3.6 音楽の埋め込みタグ

- 曲名、アーティスト、アルバムなどの静的なタグは、ファイルに埋め込まれたタグを直接書き換える。
- 書き換えの手順
  1. 一時ファイルにコピーする
  2. タグを書き込む
  3. 再パースして検証する
  4. payload ハッシュが変わっていないことを確認する
  5. rename で置き換える
- 変更前の値はジャーナルに記録する。
- 評価のように流動的な情報はファイルに書き込まず、サイドカーに置く。

### 3.7 ジャーナル

- サーバーのインスタンスごとに、データディレクトリの `journal/YYYY-MM.jsonl` に置く（§3.1）。ワークスペースには置かない。ワークスペースを共有するほかのインスタンスの操作は載らない。
- JSONL 形式で、月ごとにファイルを分け、追記だけする。ファイル（`YYYY-MM.jsonl`）は、追記した時点の UTC の年月で選ぶ（`at` ではない）。そのため、ファイルの順序は追記の順序と一致する。`at` は渡された値のまま記録する。
- 記録する操作：アップロードの受け取り、移動、リネーム、ゴミ箱への移動、埋め込みタグの書き換え、サイドカーの紐付け直し、サイドカーの書き込み（`write_sidecar`）。
- 各行の項目：`op_id`、`plan_id`（計画からの実行なら）、`actor`（`{"user":<ID>}` か `{"agent":<ID>}`、エージェントの ID は代理するユーザーの ID）、`at`、`kind`、`before`、`after`。
- 落ちたときに途中まで書かれた最終行は、次の追記の前に `<ファイル>.torn` へ移して切り取る。改行だけが欠けていて、完全なエントリとして読める行は、改行を足して残す。
- 取り消しは、ジャーナルを逆順にたどって行う。

## 4. サーバー

### 4.1 起動とキャッシュ

- 設定ファイルに書くのは、ライブラリのパス、待ち受けアドレス、トークンとユーザー ID の対応。
- redb にはスキーマのバージョンを持たせる。作り直す（削除して新しいエポックで始める）のは、ファイルが壊れている、形式が古い、スキーマのバージョンが一致しない、別のライブラリのキャッシュである、のどれかの場合だけ。ロックが取れない（別のプロセスが開いている）場合や I/O エラーは、作り直さずに起動を失敗させる。
- 1つのホストで1つのライブラリを扱うサーバーは1つだけ。`serve` はデータディレクトリを作ったら何よりも先に（一時ファイルの掃除より前に）`<data_dir>/<アプリ名>/<ライブラリID>/server.lock` の排他ロック（advisory）を取り、終了まで持ち続ける。取れなければ「another asteria server is serving this library」と出してエラーで終わる。ロックをワークスペースに置かないのは、別のホストのサーバーがワークスペースを共有できるようにするため（NFS のロックはホストをまたいで効く）。
- キャッシュにはエポック（作るたびに新しくなる ID）を持たせる。クライアントはエポックの変化を見て、全体を同期し直す。

### 4.2 スキャン

1. 起動時に全体をスキャンする。（パス・サイズ・更新時刻）をキャッシュと比べ、差分だけ処理する。
2. 起動後は `notify` でファイルの変更を監視する。取りこぼしの保険として、定期的にも再スキャンする。
3. ファイルの種類は、拡張子とマジックバイトで判定する。photos は画像と動画、music は音声を扱い、music では同じフォルダの画像をジャケットとして扱う。
4. payload ハッシュは、スキャンの中で計算する。速さの調整はしない。一括で取り込んだ直後は、ハッシュが計算されるまでサムネイルが出ない（503 で再試行させる）が、それでよいとする（2026-10-22 決定）。
5. 持ち主のいないサイドカーは、ハッシュで照合する。候補が1つに絞れたら、自動で紐付け直してジャーナルに記録する。絞れなければクライアントに通知する。
   - payload ハッシュが同じファイルは、意図して置かれていることがある（再録盤、同じ写真を別のアルバムにも入れたもの。アップロードでユーザーが「保存」を選んだもの）。そのため、候補は次の順に絞る（2026-10-26 決定）。
     1. （ハッシュ、スコープ）が一致するファイルのうち、まだサイドカーを持たないものだけを候補にする。
     2. 候補が2つ以上あり、サイドカーに `FileHash` があれば、ファイル全体のハッシュがそれと一致するものだけに絞る。移動やリネームではバイト列が変わらないので一致し、タグの違う再録盤は外れる。一致するものが無ければ、この絞り込みはしない。
     3. それでも2つ以上残れば「曖昧」とする。
   - 照合は、移動の前にまとめて行う。候補が絞れない場合と、同じファイルを2つ以上のサイドカーが取り合う場合は「曖昧」とし、どれも動かさない。
   - 絞った候補に移動の直前でサイドカーができていた場合と、候補がハッシュを計算した後に変わっていた（サイズか更新時刻が違う）場合は「衝突」とし、動かさない。
   - 曖昧と衝突をクライアントに知らせる仕組みは後回しにする。今はログに出すだけ。
6. 原本の一時ファイル（`.<名前>.<タグ>.asteria-tmp`、以前の形の `.<名前>.asteria-tmp`）の掃除は、`serve` の起動時に一度だけ行う。スキャンのたびに行うと、書き込みキューの書き込み途中のファイルを消してしまうため。消すのは更新時刻が 24 時間より古いものだけにする。ワークスペースを共有するほかのインスタンスが書き込み中のものを消さないため。
7. スキャンを始める前に、`<root>/.asteria/library.toml` があり、その ID がサーバーの扱うライブラリの ID と一致することを確かめる。一致しなければ（ディスクが外れている、別のライブラリに差し替わっている）、何も消さずにそのスキャンを中止する。

### 4.3 書き込み

- 書き込みは、ライブラリごとに1本の書き込みキューで直列に処理する。対象は、クライアント、MCP、スキャナーからのすべての書き込み。
- 順序は「原本を書く → ジャーナルに記録 → キャッシュを更新」とする。

### 4.4 API

| エンドポイント | 用途 |
|---|---|
| `POST /rpc` | JSON-RPC。`server.info`（ハンドシェイク）、閲覧、検索、メタデータの編集、操作ログの同期、変更フィード、計画の一覧・承認・却下 |
| `GET /media/{id}/original` | 原本（Range 対応） |
| `GET /media/{id}/{preset}` | サムネイル、プレビュー、オフライン用の版 |
| `PUT /upload/{session}/{chunk}` | チャンク分割アップロード（再開できる、§4.7） |
| `/mcp` | MCP（Streamable HTTP） |

- 認証は Bearer トークンで行い、トークンからユーザー ID を引く。API の内部では常に「誰のリクエストか」を持ち回る。
- API バージョンが一致しなければ、接続を拒否する。

#### wire の約束（Plan 2 の時点）

- **`MediaItem.file_hash`**（API 2.1 で追加）：ファイル全体のハッシュ（`blake3:<hex>`）。まだ計算していなければ `null`。2.0 のサーバーは返さないので、ないときは `null` と同じに扱う。クライアントのサムネイルとオフラインキャッシュのキーに使う。
- **アイテム ID**：ライブラリ ID を名前空間、ライブラリ相対パスを名前とする UUID v5。パスから決まるので、キャッシュを作り直しても変わらないが、ファイルを移動すると変わる。
- **認証**：どのルートも、正しい Bearer トークンがなければ 401 を本文なしで返す。`Bearer` の綴りの大文字・小文字は問わない。
- **`/rpc`**：本文が 64 KiB を超えると 413。それ以外はエラーも含めて HTTP 200 で、結果は JSON-RPC のエンベロープで返す。
  - リクエストの `id` は u64。JSON として読めない本文（parse error）には `id: 0` で答える。
  - `jsonrpc` は `"2.0"` でなければ INVALID_REQUEST。パラメーターのないメソッドは `params` を省略してよい（`{}` と同じ）。
  - API バージョンの確認はクライアントが行う（`check_handshake`）。サーバーが `API_MISMATCH` を返すことはない。
  - READ_ONLY と BUSY のメッセージは固定文で、サーバーのパスを含まない。READ_ONLY は「sidecar is malformed; fix or remove it to edit」、BUSY は「another write is in progress; retry」。詳細はログにだけ出す。`read_only_reason` も壊れている理由だけで、パスは含まない。
- **`/media/{id}/original` と `/media/{id}/{preset}`**：
  - 404：ID が未知、ファイルがない、プリセット名が未知、またはファイルが（シンボリックリンクを解決すると）ライブラリの外か `.` で始まるディレクトリの中にある、または XMP サイドカーである。この確認はリクエストのたびに行う。
  - 422：処理不可（ファイルが変わるまで再試行しない）。
  - 503 と `Retry-After: 2`：ハッシュがまだない、ファイルがスキャンの後に変わっている（再スキャンを依頼する）、外部ツールがない、生成待ちの列がいっぱい。
  - 原本は、スキャンの後に変わっていてもファイルがあれば返す（Range 対応）。
  - どちらのルートも `X-Content-Type-Options: nosniff` を付ける。サムネイルは `Cache-Control: private, no-cache`。

### 4.5 メディア処理

- ffmpeg と vips を子プロセスとして呼ぶ。タイムアウトと同時実行数の上限を設ける。
- 生成物は（ファイル全体のハッシュ、プリセット名）をキーにキャッシュする。ファイル全体のハッシュは `file/1` スコープの BLAKE3 で、スキャンのときに payload ハッシュと一緒に計算してキャッシュに持つ。EXIF の向きや ICC などメタデータだけを変えた場合も作り直される。photos の画像はメタデータをほとんど書き換えない（評価などはサイドカーに書く）ので、作り直しが増えることはない（2026-10-22 決定）。
- リクエストが来たときに生成するのを基本とする。オフライン用に指定されたものだけ、先に生成しておく。
- 失敗したファイルは「処理不可」として理由を記録する。ファイルが変わるまで再試行しない。外部ツールがないことは処理不可にしない。
- 実装の詳細（Plan 2）
  - サムネイルは縮小だけで、拡大はしない（vips は `NxN>`、ffmpeg は `min()`）。
  - vips には原本ではなく、一時ディレクトリに置いた安全な名前のコピー（Unix ではシンボリックリンク）を渡す。libvips がファイル名の末尾の `[...]` を読み込みオプションとして解釈するため。
  - ffmpeg は `-protocol_whitelist file` と、コンテナ形式の `-format_whitelist` を付けて呼ぶ。プレイリストや concat スクリプト、ネットワークを経由させないため。
  - 生成は要求したリクエストから切り離して動き、処理不可の記録も生成側で行う。リクエストがすべて去っても結果は記録される。
  - 生成待ちの列には上限（同時実行数 × 32）がある。超えた分は列に入れずに 503 を返す。順番を待っている間に、待っているリクエストがすべてなくなった生成は、実行枠を待たずにすぐ列から外し、ツールを起動しない。
- 初期のプリセット（実装時に調整する）

| プリセット | 内容 |
|---|---|
| `thumb` | 長辺 256px の WebP |
| `preview` | 長辺 1920px の WebP |
| `offline-image` | 長辺 2048px の WebP |
| `offline-audio` | Ogg Opus 96kbps。純 Rust のデコーダー（opus-pure か opuscule）が iPhone の Release で実時間の数百倍で復号できることを、検証用の試作で確かめた。詳細は §4.9 |

- music では、曲の `thumb` と `preview` はジャケットを描いたものになる（§4.9）。

### 4.6 MCP と整理計画

MCP のツールは3種類に分ける。

1. **読み取り**：検索、一覧、詳細。
2. **直接実行**：評価、タグ、説明、プレイリスト。実行者は「エージェント」として記録する。
3. **計画の作成**：移動、リネーム、ゴミ箱への移動。`plans/` にテキストで保存し、ユーザーがクライアントで承認する。

計画は、それを作ったインスタンスのデータディレクトリの `plans/` に置く（§3.1）。

承認された計画の実行手順は次のとおり。

1. 計画を作った時点から、対象のハッシュが変わっていないことを確認する。
2. 移動先が空いていることを確認する。
3. 1操作ずつ実行し、ジャーナルに記録する。

途中で落ちた場合は、再起動後に計画とジャーナルを突き合わせ、ファイルシステムの実際の状態を見て続きから再開する。

削除は、ゴミ箱（`.asteria/trash/`）への移動だけにする。完全な削除はユーザーが手動で行う。

### 4.7 アップロード

アップロードは framework に置き、photos と music の両方で使う（Plan 5 では photos だけが使う）。受け取ったファイルは常に `Inbox/` の下に置く。

- **流れ**
  1. `upload.check { hashes: [{ hash, scope }] }`：ライブラリに既にあるものを、そのパスと一緒に返す。キャッシュには（ハッシュ、スコープ）からパスを引く索引を持つ。
  2. `upload.begin { size, file_hash }`：1ファイルに1つのセッションを作り、セッション ID とチャンクサイズ（8 MiB）を返す。
  3. `PUT /upload/{session}/{chunk}`：チャンクを書き込む。同じチャンクを何度送っても結果は同じ。最後のチャンク以外は、長さがちょうどチャンクサイズでなければ 400 にする。本文の上限は、このルートだけチャンクサイズにする。
  4. `upload.status { session }`：まだ届いていないチャンクの番号を返す。
  5. `upload.commit { files: [{ session, path }], allow_duplicate }`：複数のセッションを1つの組として確定する。`path` は `Inbox/` からの相対パス。
  6. `upload.abort { session }`：セッションを捨てる。
- **確定**：ハッシュの計算とファイルの用意（コピー）は書き込みキューの外で、置く（rename）ことだけを書き込みキューで直列に行う（大きな動画のハッシュ計算やコピーで、ほかの編集を何分も待たせないため）。確定は、リクエストとは別のタスクで最後まで進む。クライアントがタイムアウトや切断で待つのをやめても、確定は終わって墓標を残し、送り直した確定はその結果を受け取る（進んでいる間は `BUSY`）。ハッシュの計算と用意を同時に行う確定は2つまでで、ほかは順番を待つ。
  1. 組のセッションを封印する（確定が終わるまで、チャンクの書き込み、破棄、掃除を受け付けない）。封印は手順 8 まで持ち続ける。
  2. すべてのチャンクが揃っていること、ファイル全体のハッシュが `begin` で申告した値と一致することを確かめる。一致しなければエラーにし、セッションは捨てる。payload ハッシュも計算する。
  3. XMP は読み込んで確かめる。壊れていれば XMP だけを捨て、警告を返す。
  4. 置く各ファイルを、組のフォルダ（無ければ作る）の一時ファイル（`.<セッション>.<タグ>.asteria-tmp`）に用意する。同じファイルシステムならハードリンク、セッションがワークスペースと別のファイルシステムにある（データディレクトリはローカル、ワークスペースは NFS、など）か、ハードリンクが使えなければ、コピーして fsync する。セッションの `data` はそのまま残る。確定が失敗したり重複が見つかったりして置かなかった一時ファイルは、作ったフォルダ（空なら）と一緒に、封印を解く前に消す。
  5. ここから書き込みキューで行う。`allow_duplicate` が `false` で、同じ（ハッシュ、スコープ）のメディアが既にあれば、何も置かずに「重複」と既存のパスを返す（クライアントの問い合わせのあとにライブラリが変わっていることがあるので、キャッシュで確かめ直す）。セッションは残すので、クライアントはユーザーに尋ねてから `true` で確定し直せる。
  6. 名前が衝突したら、組の全ファイルの最後の拡張子の前に同じ連番を付ける（`IMG_0001 (2).HEIC`、`IMG_0001 (2).MOV`、`IMG_0001 (2).HEIC.xmp`。`a.b.HEIC` は `a.b (2).HEIC`）。XMP は、大文字の `.XMP` で送られても `<メディア名>.xmp` として置く（ライブラリが読むのは小文字の `.xmp` だけ）。
  7. 用意した一時ファイルを、既存のファイルを上書きしない方法で rename して置く。組の途中で失敗したら、置いたものを消す（中身はセッションに残っている）ので、組の一部だけが残ることはない（途中で落ちた場合は除く。下の「確定の途中で落ちたとき」）。全部置けたらフォルダを fsync し、そのあとでセッションの `data` を消す。ジャーナルに記録して、再スキャンを依頼する。
  8. 組の各セッションを「墓標」にする。確定したセッションの一覧と結果（`Placed`）だけを残す。墓標（`committed.json`）は一時ファイルに書いて fsync し、rename して、フォルダも fsync する。読めない墓標（電源断で壊れたもの）は無いものとして消す。
- **確定のやり直し（冪等性）**：確定の応答がクライアントに届かないことがある（タイムアウト、接続断、アプリの終了）。同じセッションの組でもう一度 `upload.commit` が来たら、墓標に残した最初の結果をそのまま返し、何も置き直さない。墓標と未確定のセッションが混ざっている、または1回の確定の一部だけを指しているときは `INVALID_PARAMS` にする。ただし、見つかった墓標がどれも同じ確定のもので、その確定のセッションの組がちょうど送られた組なら、墓標の無いセッションがあっても（墓標を書いている途中で落ちた）その結果を返し、足りない墓標を書く。墓標への `upload.status` は、欠けたチャンクなし（`missing = []`）を返す。墓標は上限に数えず、`upload.begin` を妨げず、確定から7日で掃除する。クライアントは「確定中」の組について、まず同じ確定を送り直し、セッションが本当に消えていた（`NOT_FOUND`）ときだけ最初から送り直す。
- **確定の途中で落ちたとき**：
  - 置く前（ハッシュの計算中や用意の途中）に落ちたら、セッションは `data` ごと残るので、送り直した確定が最初からやり直す。用意した一時ファイルは、24 時間たってから起動時に掃除する。用意のために作ったフォルダは、空のまま残ることがある（掃除では消さない）。
  - rename の途中で落ちたら、組の一部だけがライブラリに残り、セッションは揃ったまま残る。送り直した確定は組全体を次の連番で置くので、残った一部と重複する（受け入れる残りのリスク）。
  - 置いたあと、`data` を消す前に落ちたら、ファイルはライブラリにあり、セッションも揃ったまま残る。送り直した確定は組をもう一度置き、次の連番で重複ができる（受け入れる残りのリスク）。
  - `data` を消したあと、墓標を書く前に落ちたら、チャンクはすべて揃っているのに `data` がないセッションが残る。これは消して `NOT_FOUND` を返し、クライアントは `upload.begin` からやり直す。ただし、同じ確定のほかのセッションの墓標がそのセッションを挙げていれば（墓標を書いている途中で落ちた、または書けなかった）、消さずにその墓標を書き足す。
- **パスの検証**：`path` は相対パスで、`..`、空の要素、`.` で始まる要素を含まないこと。区切りは `/` だけ。組の中のファイルはすべて同じフォルダに置く。
- **未完了のセッション**：データディレクトリの `uploads/<session>/` に置くので、サーバーを再起動しても残る。セッションはインスタンスごとのもので、ワークスペースを共有するほかのインスタンスからは見えない。7日間チャンクが届かなければ、起動時と定期的な掃除で消す。セッションは作ったユーザーのものとし、ほかのユーザーからは見えない（404）。
- **上限**：1ファイル 20 GiB。ユーザーごとの未完了のセッションは、合計 64 GiB、1000 個まで。超えたら `QUOTA` エラーにする。
- **重複の扱い**：payload ハッシュが同じでも別物のことがある（再録盤など）。そのため、重複を自動では捨てず、ユーザーに「保存」か「破棄」を選ばせる（2026-10-26 決定）。サーバーはクライアントの申告を信じず、確定のときに自分でハッシュを計算する。

### 4.8 アプリの拡張（2026-10-27 決定）

framework-server の RPC メソッドとキャッシュは、アプリに共通のものだけを持つ。アプリに固有のものは、アプリが `AppExtension` トレイトを実装して足す。framework にアプリ固有の知識を入れないため。

- `AppExtension` は、それまでの `MediaFilter` を置き換え、その役目も持つ。
  - `accepts(kind)`：どの種類のファイルをアイテムにするか。
  - `extract(rel, path) -> Option<Vec<u8>>`：スキャンで追加・更新したアイテムごとに呼ぶ。返したバイト列は、キャッシュの `APP_DATA` テーブル（パス → バイト列）に入る。中身の形はアプリが決める。アイテムが消えれば一緒に消す。
  - `wants_extra(rel) -> bool`：アイテムではないが、アプリが知りたいファイルか。music では `.m3u8`/`.m3u` と、ジャケットに使える画像。スキャンでパスと（サイズ、更新時刻）を `EXTRAS` テーブルに記録し、ファイルが消えれば消す。`.` で始まる名前と `.asteria/` は、アイテムと同じく対象にしない。
  - `rpc(method, params, ctx)`：共通のメソッドで扱えないメソッドを処理する。`ctx` からライブラリ、キャッシュ、リクエストしたユーザーを引ける。扱わないメソッドなら「扱わない」と返し、サーバーは METHOD_NOT_FOUND を返す。
- photos-server は、`accepts` だけを持つ実装を使う。
- `APP_DATA` と `EXTRAS` を足したので、キャッシュのスキーマは 4 になる。更新後の最初の起動でキャッシュを作り直す。
- MCP（Plan 7）でアプリ固有のツールを足すときも、この口を広げて使う。

### 4.9 music-server（2026-10-27 決定）

music-server は photos-server と同じ形のバイナリで、`AppExtension` を実装する。対象は `classify` が Audio と判定するファイル。タグは読むだけで、書き換え（§3.6）は Plan 7 で入れる。

**タグの読み取り**
- `extract` は lofty でタグを読み、`TrackTags` を返す。中身は曲名、アーティスト（複数値）、アルバム、アルバムアーティスト、ソート用のタグ（アーティスト、アルバムアーティスト、アルバム）、トラック番号、ディスク番号、年、ジャンル、長さ（ms）、埋め込み画像の有無。
- アーティストを分けるのは、タグが複数の値を持つときだけ。`;` や `feat.` では分けない。
- タグが読めない曲も一覧に出す。曲名はファイル名（拡張子を除く）にし、`tag_error` に理由を入れる。理由にサーバーのパスは含めない。

**閲覧用の索引**
- アルバムとアーティストの索引は、`APP_DATA` からメモリ上に組み立てる。別のテーブルに持たないので、スキャンと同期させる手間がない。
- キャッシュは、`APP_DATA` か `EXTRAS` を書き換えるたびに増える世代番号（プロセスの中だけのもの）を持つ。索引は、閲覧のメソッドが呼ばれたときに、世代番号が前に組み立てたときと違えば組み直す。件数だけで判断すると、タグだけを書き換えたファイルを見逃すため。

**アルバムの判定**
- 曲の「アルバムのフォルダ」は、曲のあるフォルダとする。ただし、フォルダ名が `CD1`、`Disc 2`、`Disk 3` の形（大文字・小文字を区別せず、空白は任意、数字で終わる）なら、その親とする。
- アルバムのキーは（アルバムのフォルダ、アルバム名）。アルバム名のタグがなければ、アルバムのフォルダの名前を使う。別のフォルダにある同名のアルバム（再録盤など）は混ざらない。
- アルバムアーティストは次の順に決める。
  1. アルバムアーティストのタグ。曲によって違えば、最も多いもの（同数なら名前の順で先のもの）。
  2. タグがなく、全曲のアーティストが同じなら、そのアーティスト。
  3. それ以外は `Various Artists`。
- アルバム ID は、ライブラリ ID を名前空間とし、キーから作る UUID v5。
- アルバムの曲は（ディスク番号、トラック番号、ファイル名）の順に並べる。番号のない曲は、番号のある曲の後ろに置く。
- アルバムの年は、曲の年のうち最も早いもの。

**アーティスト**
- 一覧はアルバムアーティストで作る。ソート用のタグがあれば、それで並べる。
- 1人のアーティストを開くと、そのアーティストのアルバムと、「参加している」アルバム（アルバムアーティストは別だが、曲のアーティストにそのアーティストを含むもの）を返す。
- 名前の比較は、大文字・小文字と Unicode の互換文字（全角・半角）を同一視する（NFKC ＋ 小文字化）。表示には最も多い表記を使う。

**ジャケット**
- 曲の `thumb` と `preview` は、その曲のジャケットを描いたものにする。photos と同じ URL なので、クライアントのグリッドがそのまま使える。
- 画像を探す順は次のとおり。
  1. 埋め込み画像。表紙（front cover）を優先し、なければ最初の画像。
  2. 曲のフォルダ、次にアルバムのフォルダにある、`cover`、`folder`、`front`、`album` という名前の jpg、jpeg、png、webp（この名前の順。大文字・小文字は区別しない）。`EXTRAS` から探す。
- 生成物のキーは（画像のバイト列の BLAKE3、プリセット）。同じアルバムの曲は同じ画像になるので、生成は1回で済む。
- ジャケットがない曲は 404 を返す。処理不可（422）にはしないので、あとで画像を置けば出るようになる。
- `album.get` は、ジャケットを持つ最初の曲の ID（`cover_item`）を返す。クライアントはその曲の `thumb` を使う。

**offline-audio**
- プリセット `offline-audio` は Audio のアイテムだけが対象で、要求されたときに作る。先に作っておくのは、オフラインの対象を選べるようになる Plan 8 から。
- ffmpeg で、最初の音声ストリームだけを Ogg Opus 96 kbps（VBR）に変換する。メタデータと埋め込み画像は落とす（`-map 0:a:0 -map_metadata -1`）。
- キーは（ファイル全体のハッシュ、`offline-audio`）。`Content-Type: audio/ogg` で返し、Range に対応する。
- タイムアウトはプリセットごとに持つ。サムネイルは今の値、`offline-audio` は10分。
- ffmpeg に libopus がない場合は、ツールがないのと同じ扱い（503）にし、処理不可にはしない。
- 再生用の原本は、今の `/media/{id}/original`（Range 対応）をそのまま使う。

**プレイリスト（読むだけ）**
- 編集は操作キューと一緒に Plan 8 で入れる。
- `playlist.list`：`EXTRAS` の `.m3u8` と `.m3u` を返す。ID はライブラリ ID を名前空間とし、パスから作る UUID v5。名前はファイル名から拡張子を除いたもの。
- `playlist.get`：ファイルを読み、エントリごとに曲を探す。
  - パスはプレイリストのあるフォルダからの相対パスとして解決する。`\` は `/` とみなす。絶対パスは、ライブラリの中を指していればライブラリ相対に直して使う。
  - そのパスの曲がなく、直前に `#ASTERIA-HASH` があれば、payload ハッシュで探す。見つかれば「移動済み」として返す。複数見つかれば、パスの順で先のものを使う。
  - URL や見つからないものは「見つからない」とし、元のパスと `#EXTINF` の曲名を付けて返す。
  - `.m3u` が UTF-8 として読めなければ、読めない文字を置き換えて読む。
  - 1つのプレイリストは 10,000 エントリまで読む。超えた分は捨て、`truncated` で知らせる。

**API（asteria-music-api）**
- `album.list`、`album.get`、`artist.list`、`artist.get`、`playlist.list`、`playlist.get` を足す。一覧はカーソルでページ送りする（`folder.list` と同じ形）。
- `folder.list`、`media.get`、`media.update`（評価、ラベル、キーワード。サイドカーに書く）は、photos と共通のものを使う。
- 曲は `MusicTrack`（`MediaItem` と `TrackTags`）として返す。
- エラーは既存のコード（NOT_FOUND、INVALID_PARAMS）を使う。

## 5. クライアント

### 5.1 接続とキャッシュ

- クライアントにはサーバーを複数登録できる。1件の登録（サーバープロファイル）は、表示名、URL、トークンからなる。同時につなぐのは、選んでいる1つだけ。
- 登録の一覧と選んでいるプロファイルは、クライアントの設定ディレクトリの `servers.toml` に保存する。トークンを含むので、Unix ではモードを 0o600 にする。
- 切り替えは、ステータスバー（狭い画面では Settings）から1操作で行う。接続しているサーバーに結び付いた状態（接続、閲覧中の位置、キャッシュの読み書き先）は、すべて1つのセッションにまとめる。切り替えではそのセッションを閉じて、新しいプロファイルのセッションを開く。
- クライアントのキャッシュは、プロファイルではなくライブラリ ID（`library.info` の `library_id`）ごとに分けて、`<cache_dir>/<アプリ名>/<ライブラリID>/` に置く。同じサーバーを指すプロファイルが2つあってもキャッシュは1つになり、プロファイルを消してもキャッシュは無駄にならない。
- 操作キュー（§5.2）は、プロファイルとライブラリ ID の組ごとに分ける。送り先を取り違えないため、切り替えたときに、未送信の操作を別のサーバーへ送ることはしない。
- オンラインで閲覧するときのサムネイルなどは、一時キャッシュ（古いものから消える）に置く。
- オフラインキャッシュ
  - 対象はユーザーが選ぶ。photos ではフォルダか保存したタグ検索、music ではアルバム、アーティスト、プレイリスト。
  - 端末ごとに容量の上限と品質を設定する。
  - メディアは（ファイル全体のハッシュ、プリセット名）をキーにしたファイルとして保存する（§4.5 と同じキー）。
  - メタデータの写しはキャッシュ扱いとし、スキーマが変わったら取り直す。

### 5.2 操作キュー（評価、プレイリスト）

- オンラインでもオフラインでも、評価とプレイリストの編集は同じ操作キューを通す。
- 操作キューは、クライアント側で唯一再生成できないデータなので、JSONL のテキストファイルに追記で保存する。
- 操作には ID を付ける。サーバーが受け取りを確認したらキューから消す。同じ操作を再送しても、ID で重複を検知して二重に適用しない。
- マージの規則
  - 評価：時刻を比べ、後勝ちにする。時刻が同じなら、値の大きい方を採る（届く順序によらず結果が同じになる）。
  - プレイリスト：追加、削除、移動の操作単位でマージする。エントリの同一性はハッシュで判断する。
- タグや説明の編集、整理計画の承認は、オンラインのときだけ行える。

### 5.3 アップロード（photos）

- 共通部分は `asteria-framework-client` の `upload` に置く。
- 送信キューはライブラリ ID とプロファイルの組ごとに `<data_dir>/uploads/<library_id>/<profile_id>.json` に保存し（同じサーバーを別のユーザーで使っても、キューを取り違えない）、アプリを閉じても次に開いたときに続きから送る。ローカルのファイルが変わっていたら最初から送り直し、サーバーのセッションが消えていたら `upload.begin` からやり直す。
- 送信は `Session` の上で動く。別のサーバーに切り替えると止まり、戻ると続きから送る。サーバーがアップロードに対応していなければ（`upload.*` が `METHOD_NOT_FOUND`）、組を失敗にせずに送信を止め、そう表示する。
- 確定で XMP が捨てられたなど、警告つきで完了した組は、その旨と理由を表示する。
- 送る前に payload ハッシュを計算して `upload.check` で問い合わせ、既にあるものはユーザーが「保存」か「破棄」を選ぶまで送らない。その間もほかのファイルは送る。
- デスクトップ：ファイルやフォルダをドラッグ＆ドロップすると、`Inbox/` に送る。
  - フォルダは中の構造を保って `Inbox/<フォルダ名>/…` に、ファイルは `Inbox/` の直下に置く。
  - 送るのは、マジックバイトで写真・動画と判定したものと XMP だけ。それ以外は送らず、件数を出す。
  - 同じフォルダで、最後の拡張子を除いた名前が同じファイルは1つの組にする（Live Photos の HEIC と MOV、メディアと XMP）。`a.b.HEIC` の名前は `a.b` として扱う。XMP は `.xmp` を（大文字小文字を問わず）除いた名前がメディア名と一致すれば darktable 式、メディアの拡張子を除いた名前と一致すれば Lightroom 式とみなし、どちらも小文字の `<メディア名>.xmp` として送る。
  - `IMG_0001.HEIC.xmp` はそのまま送る。Lightroom 式の `IMG_0001.xmp` は、拡張子を除いた名前が `IMG_0001` のメディアが1つだけならそのサイドカーとして `<メディア名>.xmp` に名前を変えて送り、2つ以上なら送らずに警告を出す。
- iOS
  - アプリを開いたら、PhotoKit で写真ライブラリを列挙する。
  - 送信済みの識別子リスト（ローカルに保存）と照合し、まだ送っていない写真を一括で送る。
  - 開いたときに自動で始めるかどうかは設定で選べる。
  - HEIC は変換せず、原本のまま送る。Live Photos は HEIC と MOV を同じベース名の組として送る。
- 重複はクライアントが送る前に問い合わせ、サーバーも確定のときに確かめる。どちらも、ユーザーが「保存」を選んだものだけを置く（§4.7）。

### 5.4 再生エンジン（music）

- UI から独立したスレッドで動かす。デコード（symphonia）、出力（cpal）、キュー管理、次の曲への移行を、すべてこのスレッドで行う。
- UI は再生エンジンにコマンドを送り、状態を表示するだけにする。
- 再生するのは、オンラインなら原本のストリーム、オフラインならキャッシュした低音質版。
- iOS
  - AVAudioSession：再生用のカテゴリに設定し、着信などによる中断と、イヤホンを抜いたときの出力先の変化に対応する。
  - MPNowPlayingInfoCenter と MPRemoteCommandCenter：ロック画面とコントロールセンターに対応する。
  - Info.plist に `UIBackgroundModes = audio` を設定する。

### 5.5 プラットフォーム差

- 1つのアプリにつき1クレートとする。
- プラットフォーム固有の処理は `#[cfg(target_os = "ios")]` のモジュールに隔離する。
- 画面幅に応じて、レイアウトをタッチ向けに切り替える。
- iOS 向けには staticlib をビルドし、`<アプリ>/ios/` の Xcode プロジェクトで包む。

### 5.6 共通の UI 部品（asteria-framework-client）

- サムネイルのグリッド
- 接続設定（サーバーの登録の一覧、追加・編集・削除、切り替え）
- オフラインキャッシュの管理画面
- 整理計画の承認画面（変更の一覧、まとめての承認と却下）

## 6. エラー処理

| 事象 | 対応 |
|---|---|
| キャッシュが壊れている、形式やスキーマが古い、別のライブラリのもの | 削除して作り直す。サーバーは止めない。ロックが取れない場合や I/O エラーは作り直さず、起動を失敗させる |
| 同じホストで同じライブラリのサーバーが2つ起動された | 2つ目はデータディレクトリの `server.lock` を取れず、何も触らずにエラーで終わる |
| ライブラリのディスクが外れた、別のライブラリに差し替わった | スキャンを中止し、キャッシュから何も消さない |
| 原本の書き込み中に落ちた | 一時ファイルから rename するので、古い版か新しい版のどちらかが残る。残った一時ファイルは、24 時間たってから起動時に掃除する。名前にプロセスごとのタグが入るので、残っていても次の実行の書き込みは妨げない |
| メディアとサイドカーの移動の間に落ちた | 取り残されたサイドカーを、ハッシュで照合して自動で紐付け直す |
| 計画の実行中に落ちた | ジャーナルとファイルシステムの状態を照らし合わせ、続きから再開する |
| XMP が壊れている | 上書きしない。警告を付けて読み取り専用にする |
| 書き出した XMP が読み戻すと一致しない | 書き込まずにエラーにする。元のファイルはそのまま残る |
| メディアを処理できない | 理由を記録する。ファイルが変わるまで再試行しない |
| 通信が切れた | クライアントは自動でオフライン動作に切り替える。操作キューはテキストで残る |
| API バージョンが一致しない | わかりやすいメッセージを出して接続を拒否する |

## 7. テスト

- **payload ハッシュ**：形式ごとにテスト用ファイルを用意する。メタデータだけを変えた版はハッシュが同じになり、画素や音声が違う版はハッシュが違うことを確認する。テスト用ファイルは、生成スクリプトと一緒にリポジトリに入れる。
- **XMP**：読み込んで書き戻したとき、asteria が知らない項目が保持されることを、正解ファイルと比べて確認する。
- **ジャーナル、計画、取り消し**：わざと途中で落とすテストを入れ、どこで落ちても原本が一貫した状態で再開できることを確認する。
- **操作のマージ**：proptest を使い、操作が届く順番によらず結果が同じになることを確認する。
- **キャッシュの作り直し**：キャッシュを削除して作り直したとき、元と同じ状態になることを確認する。
- **結合テスト**：一時ディレクトリのライブラリでサーバーを起動し、JSON-RPC、バイナリの送受信、MCP を通しで確認する。
- **CI**：Linux（x86_64 と arm64）、macOS、Windows でビルドとテストを行い、`cargo deny` を実行する。macOS では iOS 向けのビルドが通ることも確認する。vips と ffmpeg を入れるのは Linux のジョブだけで、ほかではこれらを使うテストは理由を出してスキップする。シンボリックリンクやシェルスクリプトに頼るテストは Unix だけで動かす。
- **結合テスト（photos-server の e2e）**は Linux だけで動かす（`XDG_CACHE_HOME` でキャッシュを分け、`kill -INT` で止めるため）。
- **iOS 実機**：検証用の試作とチェックリストで、手動で確認する。

## 8. リスクと早期検証

実装計画の早い段階で、次の点を試作で確かめる。

1. iOS 上で eframe / egui が起動し、タッチ操作とセーフエリアが実用的に扱えること。
2. 画面ロック中も音声の再生が続き、ロック画面から操作できること（AVAudioSession と MPRemoteCommandCenter を objc2 で使う）。
3. 純 Rust で Opus をデコードできるか。これでオフライン用の音声形式を決める。
4. PhotoKit の列挙と原本データの取得（HEIC、Live Photos）が objc2-photos でできること。

2026-10-25：4項目とも試作で確かめた。結果は `docs/superpowers/spikes/2026-10-23-ios-spike.md` にある。Opus は opus-pure と opuscule が合格したので、オフライン用の音声は Ogg Opus にする。実機ではキーボードの表示（`check.display.keyboard`）が NG だった。これは corundum-framework 側の課題とする。

## 9. 実装の順序（概要）

詳しくは実装計画で決める。iOS のウィンドウは corundum-framework の対応を待つため、iOS のクライアントは最後に回し、それまではデスクトップ向けに進める（2026-10-25 決定）。

1. ワークスペースの土台、`*-api`、ライセンス、CI。（Plan 1、済）
2. framework のコア：ライブラリ、XMP、payload ハッシュ（第1段階）、ジャーナル。（Plan 1、済）
3. framework-server：スキャン、キャッシュ、JSON-RPC、バイナリの配信。photos-server。（Plan 2、済）
4. 早期検証の試作（iOS）。（Plan 3、済。コードは削除した）
5. framework-client と photos のデスクトップクライアント：閲覧、評価とタグの編集、複数サーバーの登録と切り替え。（Plan 4、済）
6. photos のアップロード：再開できるチャンク分割アップロード、`Inbox/`、デスクトップのドラッグ＆ドロップ、重複したときの選択、サイドカーの `FileHash` と紐付け直しの絞り込み。（Plan 5）
7. music。2つの計画に分ける（2026-10-27 決定）。
   - music-server：アプリの拡張（§4.8）、タグの読み取り、アルバム・アーティスト・プレイリストの閲覧、ジャケット、`offline-audio`（§4.9）。（Plan 6a）
   - music のデスクトップクライアントと再生エンジン（§5.4）。（Plan 6b）
8. MCP と整理計画、承認画面。（Plan 7）
9. オフラインキャッシュと操作キュー。（Plan 8）
10. payload ハッシュの第2段階。（Plan 9）
11. iOS のクライアント（photos のアップロード、music のバックグラウンド再生）。corundum-framework が iOS のウィンドウに対応してから始める。

デスクトップ向けに進める間も、iOS に戻れるように次を守る。

- OS 固有の処理は `#[cfg]` のモジュールに分ける。ファイルダイアログやドラッグ＆ドロップは、デスクトップ側のモジュールにだけ置く。
- ディレクトリは `corundum_framework::dirs` を通してだけ取る。
- 画面は corundum の Shell に乗せ、狭い幅でも使えるようにする。
- `asteria-framework-client` は eframe に依存しない（egui だけ）。CI の macOS ジョブで、このクレートを `aarch64-apple-ios` 向けに `cargo check` する。
