# Plan 7b: MCP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/mcp` で MCP サーバーを開き、エージェントが閲覧、サムネイル、評価・タグの編集、`dry_run` 付きのファイル操作と取り消しを行えるようにする。あわせて、長いまとまりが待ち時間で切れないよう `organize.status` を足す（#37）。

**Architecture:** MCP のツールは既存の RPC メソッドへの薄い入口にする。ツールごとに名前、説明、手書きの入力 JSON Schema、対応する RPC メソッドを持ち、呼ばれたら `/rpc` と同じ `dispatch` に実行者 `Actor::Agent` を付けて渡す。アプリのツールは `AppExtension::mcp_tools()` で足す。`organize.apply` / `organize.undo` は最大 10 秒待って、終わらなければ `running` を返し、結果はメモリの記録帳（`BatchBook`）から `organize.status` で取る。

**Tech Stack:** Rust 1.99.0（edition 2024）、axum、rmcp 3.8.0（`server`、`transport-streamable-http-server`）、tokio。

**Spec:** `docs/superpowers/specs/2026-10-22-asteria-design.md` の §4.6（「長いまとまり」「MCP」）と §4.8（`mcp_tools`）。

## Global Constraints

- ツールチェインは `1.99.0`、edition 2024。CI は clippy `-D warnings`、`cargo fmt --check`、`cargo deny check` を通し、Linux（x86_64、arm64）、macOS、Windows でテストする。手元では `cargo clippy --workspace --all-targets --target x86_64-pc-windows-gnu -- -D warnings` も通すこと。
- `*-api` crate が依存してよいのは `serde` と `grain-id` だけ（schemars も入れない）。`asteria-framework-api` は Plan 7a の 2.3.0 がまだ出ていないので、この計画では上げない。`asteria-music-api` も変えない。
- rmcp は `asteria-framework-server` にだけ足す：`rmcp = { version = "3.8.0", default-features = false, features = ["server", "transport-streamable-http-server"] }`。テストでは dev-dependency として `features = ["client", "transport-streamable-http-client-reqwest"]` も使ってよい。
- 書き込みはすべて書き込みキュー（`Writer`）を通す。順序は「原本 → ジャーナル → キャッシュ」。
- `/mcp` からの書き込みの実行者は `Actor::Agent { on_behalf_of: <トークンのユーザー> }`。`/rpc` からは `Actor::User(user)`（今までどおり）。アップロードは MCP に出さないので `User` のまま。
- RPC のエラーにも MCP のツール結果にもサーバーの絶対パスを入れない。トークンと `Authorization` ヘッダーはログに出さない。
- `/mcp` はほかのルートと同じ Bearer 認証の内側に置く。トークンが無ければ 401（本文なし）。
- 値
  - `APPLY_WAIT = 10 秒`（`organize.apply` / `organize.undo` が待つ長さ）
  - `BOOK_KEEP = 64`（メモリに置く終わったまとまりの数）、`BOOK_KEEP_FOR = 6 時間`
  - `MAX_PREVIEW_ITEMS = 4`

## Review Focus

1. **実行者の取り違え**：MCP からの `media_update`、`organize_apply`、`organize_undo` はジャーナルで `{"agent": <ユーザー>}`、同じ操作を `/rpc` からすると `{"user": <ユーザー>}`。読み取りは実行者で動きが変わらない。→ Task 2 でテストする
2. **RPC のエラーをツールのエラーとして返す**：存在しない ID、`dry_run` で全部飛ばした結果、`ALREADY_UNDONE` などは MCP のプロトコルのエラーではなく `isError: true` のツール結果で、RPC と同じ文言。絶対パスを含まない。知らないツール名だけがプロトコルのエラー。→ Task 2 でテストする
3. **認証なしの `/mcp`**：トークンなし・間違ったトークンは 401 で本文なし。ログにトークンが出ない。→ Task 2 でテストする
4. **待ちきれないまとまり**：10 秒を超えたまとまりは `running: true` と `batch_id` を返し、そのまま最後まで進む。`organize.status` が実行中、終わった後の結果、記録帳から消えた後のジャーナルの要約、途中で落ちたもの（`complete: false`）を返す。→ Task 1 でテストする
5. **サムネイルが無い・作れない**：作成中、作れない、音楽でジャケットが無い、知らない ID のどれも、呼び出し全体は失敗させず、そのアイテムだけ文字で知らせる。5 件以上は `isError`。→ Task 3 でテストする

**Files:**

- Test: `crates/asteria-framework-server/src/batches.rs`（単体）、`crates/asteria-framework-server/tests/{organize.rs,app_ext.rs}`

**Interfaces:**
- Produces（api）:
  - `OrganizeResult` に `#[serde(default)] pub running: bool` を足す。
  - `pub struct OrganizeStatusParams { pub batch_id: String }`
  - `pub struct OrganizeStatus { pub batch_id: String, pub running: bool, pub complete: bool, pub done: u32, pub skipped: u32, #[serde(default, skip_serializing_if = "Option::is_none")] pub results: Option<Vec<OpResult>> }`
    - 実行中：`running = true`、`complete = false`、`done = skipped = 0`、`results = None`
    - 記録帳にあり終わった：`running = false`、`complete = true`、数は結果から、`results = Some(..)`
    - 記録帳に無くジャーナルにある：`history` の要約から（`complete` は終わりの行の有無）、`results = None`
  - `pub const ORGANIZE_STATUS: &str = "organize.status";`
- Produces（server、`batches.rs`）:
  - `pub(crate) struct BatchBook`（`Mutex` の中に、まとまりの ID ごとの `Slot`）。`pub(crate) enum Slot { Running, Done(Vec<OpResult>), Failed }`
  - `BatchBook::start(&self, id: BatchId)`、`finish(&self, id: BatchId, results: Vec<OpResult>)`、`fail(&self, id: BatchId)`、`get(&self, id: BatchId) -> Option<Slot>`
  - 終わったもの（`Done`、`Failed`）は、終わった時刻から `BOOK_KEEP_FOR` を過ぎたら、また `BOOK_KEEP` 件を超えたら古い順に消す。`Running` は消さない。消すのは `finish` / `fail` / `get` のついででよい（専用のタスクは要らない）。時刻は `std::time::Instant`。テストのために `BatchBook::with_limits(keep: usize, keep_for: Duration)` を持つ。
- Produces（`Writer`）:
  - `organize` の戻り値の `Batch` に `pub running: bool` を足す。
  - `Apply` と `Undo` では、`BatchId` を `organize` の中で（タスクを立てる前に）作り、`book.start(id)` してからタスクを立てる。タスクは終わったら `finish` か `fail` を呼ぶ。`organize` は `tokio::time::timeout(wait, handle)` で待ち、時間切れなら `Batch { id: Some(id), results: vec![], running: true }` を返す。時間内にエラーで終われば今までどおりエラーを返す（`fail` も呼ぶ）。`DryRun` は今までどおり最後まで待ち、記録帳に入れない。
  - 待つ長さは `Writer` が持ち、既定は `APPLY_WAIT`。テスト用に `AppState::set_organize_wait(&self, wait: Duration)`（`#[doc(hidden)] pub`）。
  - `pub(crate) fn book(&self) -> &BatchBook`
- RPC `organize.status`：`OrganizeStatusParams` → `OrganizeStatus`。ID として読めない、または記録帳にもジャーナルにも無い → NOT_FOUND「no such batch」。`Failed` → INTERNAL_ERROR（詳細はログだけ）。

- `running_is_never_evicted`：`with_limits(1, 0 秒)` で `start(a)`、`start(b)`、`finish(b, ..)` の後も `get(a) == Some(Running)`。

- Produces（`rpc.rs`）:
  - `dispatch` の引数 `user: UserId` を `actor: Actor` に変える（`user` は `actor` から取る）。`/rpc` は `Actor::User(user)` を渡す。`MEDIA_UPDATE`、`ORGANIZE_APPLY`、`ORGANIZE_UNDO` は受け取った `actor` を使う。
  - `pub(crate) async fn call(state: &AppState, actor: Actor, method: &str, params: Value) -> Result<Value, RpcError>`（`dispatch` を呼ぶだけ）
- Produces（`writer.rs`）: `Writer::update(&self, actor: Actor, params: MediaUpdateParams)`。`do_update` も `actor` を受け取り、`update_sidecar` に渡す。
- Produces（`ext.rs`）:
  - `pub struct McpTool { pub name: String, pub description: String, pub input_schema: serde_json::Map<String, serde_json::Value>, pub method: String }`
  - `AppExtension::mcp_tools(&self) -> Vec<McpTool> { Vec::new() }`
- Produces（`mcp.rs`）:
  - `pub(crate) fn framework_tools() -> Vec<McpTool>`：下の表
  - `pub(crate) struct AsteriaMcp { state: AppState, tools: Arc<Vec<McpTool>> }`。`tools` は `framework_tools()` に `ext.mcp_tools()` を足したもの。名前が framework のものと重なったアプリのツールは捨てて `tracing::warn!` を出す。
  - `rmcp::ServerHandler` を手で実装する（ツールは動的なのでマクロは使わない）：
    - `get_info`：tools の capability と、下の instructions。
    - `list_tools`：`tools` をそのまま。
    - `call_tool`：名前で引き、`call(state, Actor::Agent { on_behalf_of: user }, method, arguments)`。`Ok(v)` は JSON を整形した文字 1 つの `CallToolResult::success`、`Err(e)` は `e.message` の文字 1 つの `CallToolResult::error`（`isError: true`）。知らない名前はプロトコルのエラー（`invalid_params`）。
    - `user` は、rmcp がリクエストの文脈に入れる `http::request::Parts` の `extensions` から、認証の層が入れた `UserId` を取る。無ければプロトコルのエラー（ここに来るのは設定の誤りだけ）。
  - `app.rs`：`/mcp` に `rmcp::transport::streamable_http_server::StreamableHttpService` を `nest_service` で置く。認証の `layer` の前に足して、認証の内側に入れる。セッションは `LocalSessionManager`。本文の上限は `/rpc` と同じ `BODY_LIMIT`。
- framework のツール（`name` → `method`）：`library_info` → `library.info`、`folder_list` → `folder.list`、`media_get` → `media.get`、`media_update` → `media.update`、`organize_apply` → `organize.apply`、`organize_status` → `organize.status`、`organize_undo` → `organize.undo`、`organize_history` → `organize.history`。`description` は英語で、そのツールが何をし、何を返すかを 1〜3 文で（`organize_apply` には「大きな変更の前に `dry_run: true` で結果をユーザーに見せる」「`running` が返ったら `organize_status` で待つ」、`organize_undo` には「取り消しもまとまりで、取り消せばやり直しになる」を入れる）。`input_schema` は api の Params 型の各フィールドを手で JSON Schema にしたもの（`"type": "object"`、`properties`、`required`、`"additionalProperties": false`）。
- instructions（そのまま使う）:

```text
Asteria manages a self-hosted media library. Browse with folder_list and media_get; look at pictures with media_preview. Edit ratings, tags and descriptions with media_update. Move, rename and trash files with organize_apply: run it with dry_run: true first and show the user the result before a large change, and give every batch a label that says what it does. If organize_apply or organize_undo answers running: true, poll organize_status with the batch_id. Every batch can be undone with organize_undo; nothing is ever deleted for good.
```
